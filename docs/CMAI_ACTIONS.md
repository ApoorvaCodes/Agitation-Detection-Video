# Hitting and kicking candidate detector

Items `cmai_07_hitting` and `cmai_08_kicking` are distinct canonical labels in detector
bundle **1.1** (`detector_mode: interaction_actions`). The normal shipped bundle
is unchanged. `configs/cmai_action_detector_bundle.json` declares both items but
has **no enabled rules or assets**. No permitted event-labelled footage or action
checkpoint was found in the repository. Empirical comparison and user release
remain pending. Synthetic tests verify algorithms and contracts only.

## Representation and model choices

The baseline supervised classifier has two masked centroids per item: explicitly
labelled positive and negative training embeddings. It reuses Person 2's masked
cosine/fusion and configurable pose/encoder interfaces. The experiment command
compares pose statistics, motion statistics, pose+motion, and pose time bins+motion
using the same windows and splits. A fifth comparison optionally adds frozen
Torchvision R3D-18 video features to the temporal representation. There is no
claim that a representation is best, no fine tuning, and no calibration.

Bundles pin configuration, pose representation/bins, action model identity/version,
asset SHA-256, and optional video model/checkpoint/preprocessing identities. Fusion
space hashes include component spaces, dimensions, weights and window duration.
Numeric configuration fields are canonical floats across JSON/worker boundaries.
Mismatches reject inference. Older assets hashed from direct integer-valued Python
settings need rebuilding; assets built from ordinary float JSON settings retain
their spaces. Missing video features in a video-enabled bundle
abstain instead of silently falling back to pose. Missing/shared coordinates and
zero norms remain unavailable evidence.

R3D-18 is **optional** and has not been run with real weights here. Its source is
Torchvision's [R3D-18 documentation](https://docs.pytorch.org/vision/2.0/models/generated/torchvision.models.video.r3d_18.html)
and [implementation](https://github.com/pytorch/vision/blob/main/torchvision/models/video/resnet.py).
The specified checkpoint is
`https://download.pytorch.org/models/r3d_18-b3b3357e.pth` (`KINETICS400_V1`, about
127 MB). Review its permitted use and obtain it explicitly; the code never
downloads it. Compute the full SHA-256 of the obtained file and put it in a local
encoder JSON (replace both placeholders):

```json
{
  "model": "torchvision_r3d_18_kinetics400_v1",
  "checkpoint_file": "/absolute/local/r3d_18-b3b3357e.pth",
  "checkpoint_sha256": "REPLACE_WITH_FULL_64_CHARACTER_SHA256",
  "source": "https://download.pytorch.org/models/r3d_18-b3b3357e.pth",
  "clip_frames": 16,
  "sample_fps": 15
}
```

Install the existing `.[models]` extras for pinned torch/torchvision. The adapter
loads a strict local state dict using `weights_only=True`, replaces the classifier
with 512-dimensional features, and runs inference on CPU. It samples 16 RGB frames
at 15 fps from each window start. The ROI is the union of the actor and that actor's
visible target boxes, resized to 171×128 before the official enum transforms
(112 crop and normalization). ROI resizing can distort aspect ratio; this
preprocessing is versioned and needs evaluation. Tail windows, failed decoding,
unknown actor identity or empty crops yield masked video features. Kinetics action
labels are never mapped directly to CMAI. The default comparison window is 16/15
seconds, allowing this option without changing the other representation windows.

## Evidence and event semantics

Engineering defaults are 16/15-second half-open windows, 75% overlap, gaps above
0.35 seconds breaking segments, at least 3 samples and 80% expected valid samples.
Rules generated by experiments require 80% visible limb/motion observations,
actor/target detection confidence ≥0.6 and raw landmark visibility ≥0.7. Hitting
uses a measured shoulder/elbow/wrist on the contacting side; kicking uses
hip/knee/ankle. At least one corresponding valid joint speed is required.
Interpolated boxes/poses cannot supply support. These defaults are design choices,
not validated operating points.

A separately supplied, timestamped **contact evidence sidecar** identifies the
actor track, hand/foot, target kind (`person`, `self`, `object`), target ID and
normalized box. Each row requires inspected frame/evidence reference, actor-limb
and target visibility, and `observed`, `absent`, or `unclear` contact. Its provider
identity/version, annotation protocol, recording hash and video ID are recorded.
Source frames/timestamps and person/self target boxes must match P1. Object
identity/visibility are supplied by the reviewed/external provider; P1 does not
perform object or contact detection. Provider assertions require independent
quality assessment; they are not geometric proof. Proximity or overlapping boxes
alone cannot supply observed contact.

No provider, missing contact, inadequate visibility, unclear contact, conflicting
targets, insufficient shared embeddings or missing required video features cause
an explicit item/window abstention. `absent` contact is an assessed non-candidate
only when reviewed across at least 80% of the window. Even observed contact needs
both positive-centroid cosine and positive-minus-negative cosine margin thresholds
plus consecutive temporal support. Ordinary movement and benign contact must be
represented as explicit negatives. The raw and smoothed positive cosine must
both pass; EMA resets at abstentions/gaps. At least two consecutive overlapping
windows and a 0.2-second interval are required by generated rules. A target change,
segment gap, non-candidate or abstention ends support. Overlapping windows are
correlated and are not independent confirmation. Brief or sparsely sampled strikes
can be missed; validate timing and sample rate before use.

Events remain **candidate** actions linked to one actor track and one target,
with supporting chunks, frames, contacts and clips. `score` is actual uncalibrated
positive-centroid cosine, never probability. The sidecar reports negative cosine
and contrast margin separately; neither is calibrated. A reviewed candidate never
changes the original model score. There is no inference of intent, injury,
clinical cause, severity or CMAI's two-week frequency rating. Person 3's machine
verification cannot proceed on contactless hitting/kicking packets and never
substitutes for human review.

## Permitted annotations and experiments

Use [action annotation schema](cmai.action-annotations.schema.json). Provenance
requires dataset name/source, permission/license, protocol/version and label
agreement. Each recording entry supplies local perception/contact files, optional
original video, recording SHA-256, actor track/global subject, **every visible
track's global subject mapping**, all participant IDs, session ID and explicit
train/validation/test split. Audit rejects cross-split subjects (including targets),
sessions, recording hashes, P1 file hashes and video IDs, missing tracks,
contradictory identities and duplicate actor/recording entries. Dataset owners must
verify global identities and permissions; hashing cannot detect edited copies of
the same recording or false identity declarations. Original bytes are checked when
a video path is present; a declared hash alone is marked unverified in the audit.

Annotations are non-overlapping per actor/item and have unique IDs, start/end and
`positive`, `negative` or `ambiguous` outcomes. Positive events require reviewed
target kind/ID. Establish an operational protocol for a visibly forceful hand/arm
strike (07) or foot/leg strike (08) with visible target/contact. Include walking,
waving, dancing, leg stretching, harmless touches/high-fives, camera cuts and
other plausible confounders as permitted, reviewed negatives. Ambiguous intent is
not automatically an observable-action negative; unclear contact/visibility belongs
in ambiguous examples. Never stage harmful acts or create labels from model output.

Only fully contained, quality-gated **train** positive/negative chunks form
centroids. Ambiguous windows and boundary-straddling labels are excluded from
training; unlabeled time is unknown, not a negative. Both outcomes are required
for every declared item/representation; otherwise that variant remains pending.
Contact evidence must be independently produced with the same protocol across all
splits, without looking at action ground-truth labels. Supplying label-derived
contact assertions would leak ground truth and invalidate evaluation.

```sh
PYTHONPATH=src python -m cmai.action_experiments \
  --manifest /absolute/permitted/actions.json \
  --output-dir experiments/actions-run-001 \
  --thresholds 0.6 0.8 0.9 --margins 0 0.1 0.2
# Optional fifth variant, using the explicit encoder JSON above:
PYTHONPATH=src python -m cmai.action_experiments \
  --manifest /absolute/permitted/actions.json \
  --output-dir experiments/actions-video-run-001 \
  --video-encoder /absolute/local/r3d-encoder.json
```

A shared optional `--config` accepts Person2Config JSON; video comparisons require
16/15-second windows for every variant. Threshold and margin are chosen **only on
validation** event micro F1 with nonzero observed coverage (ties select larger
threshold, then larger margin). Held-out test is evaluated once per representation
per command. Do not repeatedly use test feedback to choose models or configurations.
Freeze splits, protocol, search grid, acceptance criteria and dataset before running.

Reports record provenance, manifest/file/code hashes, runtime, configurations,
encoder/model identity, unusable training examples, complete validation grid,
selected thresholds, validation/test predictions and metrics. Event matching is
greedy one-to-one, target-aware, temporal IoU ≥0.5. Reported held-out metrics include
per-item TP/FP/FN, precision/recall/F1, micro F1, matched IoU and signed/absolute
onset/offset timing error, evaluable-window coverage, positive/negative abstentions,
reasons, ambiguous windows and excluded predictions. Unobserved/ambiguous predictions
are excluded, not false negatives; missed explicitly positive events count as FN
even during abstention. Coverage is over annotated overlapping windows; interpret
it alongside event metrics. Empty denominators give null, never fabricated zeros.
The committed readiness report contains null metrics and no model selection.

Evaluated runs emit `<variant>.action-model.json` and `<variant>.bundle.json` in
**research** mode. Choose explicitly; reports never declare an automatic winner.
Use a resulting bundle through `CMAI_DETECTOR_BUNDLE` and the same independent
contact evidence provider. The older positive-only bundle packaging CLI is for
items 01/26/29 and does not package these supervised action assets.

## Contracts and release

P1 and P2 strict JSON **1.0 remain compatible**. Action review additionally needs
[CMAI camera result 1.1](cmai.camera-result.schema.json), including action assessments
and event contacts. Legacy 1.0 companion payloads remain readable. The independent
[contact evidence](cmai.interaction-evidence.schema.json),
[action model](cmai.action-model.schema.json) and
[assessment](cmai.action-assessments.schema.json) schemas have explicit version IDs.
Do not discard the companion sidecar when handing off actions to Person 3. The
legacy P2 candidate JSON alone cannot prove contact for machine review.

Before enabling either item for users, provide permitted representative labelled
footage, an audited independent contact provider, subject/session-disjoint held-out
results, frozen validation thresholds, sufficient positive and negative examples,
and tested upload→review→frame/clip→export evidence. Optional R3D also needs the
explicit approved checkpoint/hash. Existing release gates require a matching
hashed evaluation report, matching code/config/model/rules/quality settings,
reviewer-specified per-item minimum precision, recall, event F1, coverage and test
positive counts, negative interval counts, and an explicit per-item
`max_mean_absolute_timing_error_seconds` (mean of the worse absolute onset/offset
error per matched event), plus permission/protocol/evidence-path and named approval records.
These thresholds are not invented here. Each item must pass independently; creating
a research bundle does not release it. Human review and clinical validation remain
Person 3/project-review responsibilities.

initialization, P2 aggregation, companion schema parsing and ZIP export using the
existing local `yolo11n.pt` and a generated non-human two-second clip. It found
zero tracks/poses/candidates. This proves limited runtime mechanics only. Human
tracking/pose quality, track continuity, action accuracy and human review on real
footage remain unvalidated.

Run this command from a normal Terminal in the logged-in graphical Mac session,
using a permitted local video and a fresh output directory:

```sh
source .venv/bin/activate
PYTHONPATH=src python -m cmai.runtime_validation \
  --input /absolute/permitted/video.mp4 \
  --output-dir /absolute/local/validation-run-001 \
  --bundle configs/cmai_action_detector_bundle.json
```

`--config` accepts the existing Person1 YAML and requires an existing local YOLO
checkpoint, avoiding automatic model downloads. A trained action bundle can be
supplied with `--bundle` and independent source-linked contact JSON via
`--interactions`. The command preserves runtime/code/model hashes, worker status,
P1/P2 and camera results, per-status coverage, track/pose counts, clip statuses
and the evidence ZIP. It rejects nonempty output directories and exits nonzero
on worker failure. `runtime-report.json` explicitly distinguishes failed and
completed runs. A completed run with zero candidates does not establish a
behaviour negative; check enabled items and coverage/abstentions.

Before declaring real-video validation complete, inspect actual source frames:
correct actor/target association, visible wrists/ankles, valid masks, timestamp
alignment, gaps/swaps, evidence clip boundaries and reviewer/export persistence.
Then evaluate permitted labelled events with the experiment command above. Merely
initializing a model or passing unit tests cannot satisfy those checks.
